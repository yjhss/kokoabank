# Schema Migration — Flyway 기반 데이터베이스 스키마 관리

## 1. 도입 배경

개발 및 운영환경에서 일관된 데이터베이스 스키마를 유지하고, 스키마 변경사항을 Git과 함께 관리하기 위해 Flyway를 도입하였다.

## 2. 선정 이유

- 버전별 SQL 마이그레이션 파일 관리
- 새로운 DB 환경에서도 동일한 스키마 재구성
- 마이그레이션 적용 이력 관리
- 애플리케이션 시작 단계의 자동 스키마 검증
- CI/CD 파이프라인과 연동 가능

## 3. 구현 방법

마이그레이션 파일은 `backend/src/main/resources/db/migration`에 저장한다.

최초 스키마는 `V1__create_banking_tables.sql`로 생성하였다.

Spring Boot에서 Flyway를 활성화하고 Hibernate의 `ddl-auto`를 `validate`로 설정하여 스키마 생성과 검증의 책임을 분리하였다.

## 4. 마이그레이션 운영 원칙

1. 이미 적용된 마이그레이션 파일은 수정하지 않는다.
2. 변경사항은 새로운 버전의 SQL 파일로 작성한다.
3. 로컬 및 테스트 환경에서 검증한 후 배포한다.
4. 운영 DB의 변경은 백업, 호환성, 잠금 영향 및 복구 계획을 검토한다.
5. 배포 순서에 따라 애플리케이션과 데이터베이스의 호환성을 유지한다.

## 5. 검증 방법

```sql
SELECT installed_rank, version, description, success
FROM flyway_schema_history;
```

성공적으로 적용된 마이그레이션의 버전과 성공 여부를 확인한다.

## 6. 기대 효과

- 환경별 DB 스키마 불일치 방지
- 데이터베이스 변경 이력 추적
- 신규 개발환경 구성 절차 단순화
- 자동화 테스트에서 일관된 DB 구조 확보

## 7. 향후 확장

- V2 이상 스키마 변경 실험
- CI 단계에서 마이그레이션 검증
- 운영 DB의 Expand/Contract 마이그레이션
- 변경 실패 대응 및 데이터 복구 절차
